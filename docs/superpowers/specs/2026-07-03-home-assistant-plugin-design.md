# Home Assistant Plugin — Design

## Context

OpenACM currently controls smart-home devices through `src/openacm/tools/iot/`: a
`DeviceRegistry` (JSON-file persistence), a `BaseDriver` abstraction, and three
vendor-specific drivers (Tuya, LG TV, Miio) plus LAN discovery. Every new
vendor needs its own driver, its own pairing tool, and its own quirks handled
by hand.

This is **Phase 2** of the plugin-system roadmap (Phase 1 — the plugin
dashboard, `get_config_schema()`/`has_custom_ui()` — already shipped). Phase 2
replaces the whole `tools/iot/` subsystem with one plugin that talks to a
running [Home Assistant](https://www.home-assistant.io/) instance instead of
to individual devices. Home Assistant already normalizes Tuya, Xiaomi/Miio,
LG WebOS, and hundreds of other integrations behind one stable API — so
OpenACM no longer needs any vendor-specific code at all, just one HTTP/
WebSocket client.

## Goals

1. Control any Home Assistant entity (lights, switches, climate, covers,
   media players, etc.) from chat/voice, including targeting several
   entities or a whole area in a single action.
2. Activate Home Assistant scenes by name.
3. A `/home-assistant` dashboard page showing live device state, with
   inline controls — no need to ask the agent for routine actions.
4. Real-time state end-to-end: a change made from anywhere (HA app, physical
   switch, another automation) reflects in the OpenACM dashboard within
   about a second, the same way every other real-time feature in the
   dashboard already works.
5. Retire `tools/iot/` entirely — no dual-maintenance of two device-control
   systems.

Out of scope: pairing/discovering individual devices (Home Assistant already
does this far better than OpenACM ever could — users manage devices in HA's
own UI); creating/editing HA automations from OpenACM (existing HA
automations keep running untouched, we only trigger scenes); a generic
non-HA fallback for users without Home Assistant.

## Decisions

- **One generic client, no per-device drivers.** Home Assistant's own domain
  model (`light`, `switch`, `climate`, `cover`, `media_player`, `vacuum`, ...)
  is already the abstraction layer OpenACM needs. A small "friendly verb →
  HA service" mapping (`turn_on`, `turn_off`, `toggle`, `set_brightness`,
  `set_temperature`, `open`, `close`, `stop`, `set_volume`) replaces the old
  `BaseDriver` method set, translated per-domain into the real
  `domain.service` call.
- **Auth via HA's own Long-Lived Access Token**, generated by the user from
  their HA profile page — no OAuth flow to build. Config schema (Phase 1's
  `get_config_schema()`): `ha_url` (text, required), `ha_token` (password,
  required).
- **No new dependencies.** `httpx` (REST) and `websockets` (WS) are already
  project dependencies.
- **Backend↔HA is WebSocket; backend↔browser reuses the existing EventBus →
  WebSocket broadcast pattern** already used by every other real-time
  dashboard feature (`tool.called`, `message.sent`, etc.) — not a new
  transport, just one more registered event type.
- **Multi-entity/area targeting in one call.** `ha_control` accepts a single
  `entity_id`, a list of them, or an `area` — Home Assistant's service-call
  API natively supports targeting many entities or a whole area in one
  request, so "turn off every light in the living room" is one HA API call,
  not N tool calls.
- **Every tool call is independent and never raises unhandled.** Each
  returns a structured success/failure result. When a user's single message
  implies several actions (already handled by the existing agentic
  tool-calling loop — no new orchestration needed here), one failing action
  must not prevent the rest from running or from being reported.
- **The dashboard page polls the in-memory cache, not HA directly**, so
  opening `/home-assistant` never hits Home Assistant on every page load —
  only the plugin's own long-lived WebSocket connection talks to HA.

## Data model

No new database table. Configuration (`ha_url`, `ha_token`) lives in the
existing `plugin_state.config_json` from Phase 1 — nothing plugin-specific
to add to the schema.

In-memory only, owned by `HomeAssistantClient`: a `dict[entity_id, EntityState]`
cache, rebuilt from HA's `get_states` on every (re)connect and kept current
by the `state_changed` WebSocket subscription.

## Backend changes

**New module `src/openacm/plugins/home_assistant/`:**

- **`client.py` — `HomeAssistantClient`:**
  - `async def connect()` — opens the HA WebSocket, authenticates with the
    long-lived token, calls `get_states`, subscribes to `state_changed`.
    Reconnects with exponential backoff (capped ~30s) on network drops;
    does **not** retry on an auth failure (401/invalid token) — logs once
    and stops, since retrying won't fix a bad token.
  - `async def call_service(domain, service, entity_id=None, area_id=None, **data)`
    — REST call to `POST /api/services/{domain}/{service}`.
  - `get_state(entity_id) -> EntityState | None`, `list_states(domain=None, area=None)`
    — reads from the in-memory cache.
  - On each `state_changed` message: updates the cache, emits
    `event_bus.emit("ha:state_changed", {...})`.
- **`tools.py`** (registered via `get_tool_modules()`):
  - `ha_devices(domain="", area="")` — list entities, optionally filtered.
  - `ha_control(entity_id, action, area="", **params)` — `entity_id` may be a
    single id or a list. Maps `action` + the entity's domain to the correct
    HA service and field names (e.g. `turn_on` + `light` → `light.turn_on`;
    `set_temperature` + `climate` → `climate.set_temperature`). Unsupported
    action for a domain returns a clear error, not an exception.
  - `ha_status(entity_id)` — current state + attributes; fuzzy-matches by
    name if the exact `entity_id` isn't found (mirrors the old registry's
    fuzzy lookup), suggesting close matches on a miss.
  - `ha_scenes()`, `ha_activate_scene(name)` — same fuzzy-match convention.
- **`router.py`:** `GET /devices`, `POST /devices/{entity_id}/control`,
  `GET /scenes`, `POST /scenes/{scene_id}/activate` — all read from the
  client's in-memory cache or proxy straight to `call_service`.
- **`__init__.py` — `HomeAssistantPlugin(Plugin)`:**
  - `get_config_schema()` → `ha_url`, `ha_token`.
  - `get_tool_modules()`, `get_api_router()`.
  - `get_nav_items()` → `{"path": "/home-assistant", "label": "Home Assistant", "icon": "Home", "section": "main"}`.
  - `get_intent_keywords()` → replaces the old `"iot"` block in
    `tools/intent_keywords.py` with Home-Assistant-flavored phrases (luces,
    domótica, casa inteligente, etc.) pointing at the new tool names.
  - `on_start(**app_context)`: calls `super().on_start(**app_context)` first
    (required for `get_setting()` to work, per the Phase 1 convention), then
    reads `ha_url`/`ha_token` via `get_setting()`; if both present, connects
    the client. If not configured, the plugin loads inert — no error, no
    devices, until the user fills in the config from `/plugins`.
  - `on_stop()`: disconnects the client cleanly, cancels the reconnect loop.

**Wiring `ha:state_changed` for real-time browser updates** (`src/openacm/web/server.py`,
next to the existing `event_bus.on(EVENT_TOOL_CALLED, ...)` registrations):
one `event_bus.on("ha:state_changed", on_ha_state_changed)` handler that calls
the existing `broadcast_event(...)` helper — the exact same pattern every
other real-time event already uses, no new transport.

**Retiring `tools/iot/`:**
- Delete `src/openacm/tools/iot/` in full (`base.py`, `discovery.py`,
  `iot_tool.py`, `registry.py`, `drivers/`).
- Remove the `from openacm.tools.iot import iot_tool` import in
  `src/openacm/tools/__init__.py:6` and `src/openacm/app.py:331`.
- Replace the `"iot": [...]` keyword block in `tools/intent_keywords.py`
  with the new Home Assistant keywords (see above).
- `tests/unit/test_tool_registry.py:42`'s `EXPECTED_CATEGORIES` set keeps
  `"iot"` as the category label — it's still the right functional grouping
  (device control), just HA-backed now instead of driver-backed.
- Leave `data/iot_devices.json` untouched — orphaned data from a retired
  system, not worth migrating or deleting automatically.
- Update `docs/05-tools-reference.md`'s direct tool documentation; passing
  mentions of "iot" in other narrative docs are left as-is (out of scope —
  not worth a repo-wide documentation pass for this change).

## Frontend changes

**New page `frontend/app/home-assistant/page.tsx`** (added to sidebar nav via
the plugin's `get_nav_items()`, same dynamic mechanism `gmail_classifier`
already uses — no core sidebar edit needed this time):
- Entities grouped by area (or domain, if HA hasn't assigned areas), rendered
  as cards matching the `/plugins` card-grid look (`acm-card`, same grid
  pattern) — a toggle for lights/switches, a slider for brightness, simple
  buttons for covers/media players.
- A "Scenes" section: one button per scene, click to activate.
- If the plugin isn't configured yet: an empty state pointing at
  `/plugins` → "Configurar" for `home_assistant`, reusing Phase 1's generic
  `PluginConfigForm` — no custom settings UI needed here either.

**Real-time updates:** extend `frontend/hooks/use-websocket.ts` with one
`else if (data.type === 'ha:state_changed')` branch dispatching into a new,
small `frontend/stores/ha-store.ts` (entity id → state map) — the
`/home-assistant` page reads from that store, not from polling.

## Error handling

- HA not configured or unreachable at plugin startup: logged once, plugin
  stays loaded with an empty entity set; the page shows "No se pudo
  conectar a Home Assistant — revisa la configuración," tools return a
  plain-language error instead of raising.
- WebSocket drops mid-session: reconnect with backoff; cache serves
  last-known state meanwhile (no user-facing staleness indicator — YAGNI
  for v1).
- Invalid/expired token: REST calls surface a clear "reconfigure the token"
  error to both the tool-calling LLM and the logs; the WS listener does not
  hot-loop retrying a bad token.
- Unknown `entity_id`/scene name: fuzzy-matched against known names; on a
  genuine miss, the error message lists close matches (mirrors the old
  registry's helpfulness).
- One failing action inside a multi-action user request never aborts the
  rest — every tool call returns its own success/failure, so the agent can
  report a partial-success summary ("apagué las luces pero la cortina no
  respondió").

## Testing

- Unit tests (mocked `HomeAssistantClient`, following the existing
  `mock_llm_router`-style fixture convention):
  - Verb → service mapping per domain (light, switch, climate, cover,
    media_player), including the multi-entity/area targeting path.
  - Fuzzy name matching for entities and scenes, including the
    suggestions-on-miss behavior.
  - Error paths: HA unreachable, invalid token, unknown entity/scene.
  - Config schema round-trip (reusing the Phase 1 plugin-config test
    pattern verbatim).
  - `PluginManager`/tool-registry regression: `tools/iot/` removal doesn't
    break `test_tool_registry.py`'s category expectations.
- No integration test against a real Home Assistant instance in CI (no
  access) — a manual verification pass against the user's real HA instance
  is the final implementation task, same convention as the Gmail digest
  cron.
